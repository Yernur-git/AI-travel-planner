# Ограниченный цикл планирования

Владелец: Ернур. Реализован 26 ноября 2026 в `feature/planning-loop`.
Проверки этой задачи выполняются offline, без новых обращений Gemini.
Общий контракт `1.1-draft`, `app.py`, UI и бюджет не изменены.

Публичная функция:

```python
from src.ai import plan_with_schedule
from src.ai.gemini import load_settings
from src.catalog import load_catalog

# request уже соответствует TripRequest. Этот пример при запуске вызывает Gemini.
selection = load_catalog().search(
    interests=request.interests,
    start_date=request.start_date,
    end_date=request.end_date,
)
result = plan_with_schedule(request, selection, load_settings(), max_attempts=3)
```

Сигнатура: `plan_with_schedule(request, selection, settings, *, max_attempts=3,
transfer_estimates=None, transport=gemini_transport) -> PlanningResult`.
Функция сама не читает файлы или ключи: вызывающий код передаёт TripRequest,
CatalogSelection и Settings. Одна и та же выборка используется для генерации,
проверки ссылок и расписания. Модель может выбрать только ID этой выборки.
`transfer_estimates` имеет тот же смысл, что у [check_schedule](SCHEDULE.md):
независимые направленные оценки с методом и происхождением. Они поступают
от доверенного вызывающего кода, а не из ответа LLM. Реальных оценок не добавлено.

## Порядок и лимит

1. Генерация PlanDraft из каталога. Проверяются схема, даты, ID, интересы,
   источники, основания расходов и запрет придуманных оценок переходов.
2. `check_schedule` проверяет нормализованный черновик и возвращает все issues.
3. При `invalid` следующая генерация получает предыдущий нормализованный draft,
   `known_violations` и отдельно `unknown_facts`. Каждое замечание содержит
   существующие поля Issue: code, message, date, activity_id. Часы и факты
   по-прежнему берутся из каталога; доверенные оценки переходов передаются
   отдельным списком для выбора зазоров. Каждый новый ответ проверяется заново.
4. При `valid` или `unknown` цикл останавливается. Неизвестные часы/переходы
   не являются нарушением для исправления. При сочетании известных нарушений
   и неизвестных фактов сначала исправляются известные нарушения; следующая
   проверка может закончиться `unknown`.

`max_attempts` допускает только целые 1–3, включая первую генерацию.
Каждый шаг вызывает `generate(max_attempts=1, defer_schedule=True)`, поэтому
повторы провайдера не умножают лимит. SDK по-прежнему имеет `attempts=1`.
Невалидный JSON, схема, ID или придуманная длительность тоже расходуют одну
генерацию. При них следующая попытка получает безопасный код INVALID_RESPONSE;
сырой непроверенный ответ в prompt не возвращается. Предыдущие проверенные
замечания, если были, сохраняются. Таймаут одного обращения остаётся 45 секунд;
отдельного общего таймаута этот модуль не вводит.

`defer_schedule=True` переносит проверки порядка/пересечений, повторов мест,
минимальной длительности и известных часов из провайдера в `check_schedule`,
чтобы получить конкретные замечания вместо общего INVALID_RESPONSE.
Схема и проверки каталога остаются обязательными. При прямом вызове generate
по умолчанию `defer_schedule=False`: прежнее поведение CLI сохранено.
Использовать отложенные проверки без последующего `check_schedule` нельзя.

## Результат и ошибки

PlanningResult является внутренним Python dataclass части Ернура, а не новым
общим форматом обмена. Его поля: `status`, `draft`, `schedule_check`, `metadata`.

| status | Значение |
| --- | --- |
| `schedule_valid` | Последний ScheduleCheck valid; бюджет не проверен. |
| `unknown` | Последний ScheduleCheck unknown; полная проверка расписания невозможна. |
| `attempts_exhausted` | Лимит достигнут, последний проверенный draft имеет известные нарушения. Для диагностики; не показывать как допустимый маршрут. |

`metadata` использует существующий ResultMetadata: mode=ai, текущая модель,
версия каталога, prompt_version=`gemini-schedule-loop-v1`, суммарное число
генераций этого запуска. `schedule_valid` не означает TripResult.ok.
PlanningResult не содержит BudgetSummary, стоимости или имитации бюджета.

Ошибка API (включая квоту/таймаут/отказ доступа) немедленно пробрасывается как
PlannerError с безопасным code и суммарным attempts, включая неудавшийся вызов.
Вместо неё не возвращаются demo, старый черновик или infeasible.
Если последняя генерация не прошла проверку ответа, выбрасывается
INVALID_RESPONSE; предыдущий draft не выдаётся за последний результат.
Ошибки конфигурации до первой генерации имеют attempts=0; неверный TripRequest
отклоняется существующей Pydantic-валидацией до транспорта.

## Будущая интеграция Рахата

Вызывающий код должен отдельно обработать PlannerError и все три статуса.
После `schedule_valid` можно передать `result.draft` и ценовые основания того же
снимка каталога модулю бюджета Рахата. При `unknown` необходимо сохранить issues
и явно показать неполноту проверки; при `attempts_exhausted` нельзя выдавать draft
как пригодный маршрут. Преобразование в общий TripResult, обогащение названиями,
использованными источниками и расходами остаются совместной работой.

Если бюджет позже потребует исправления моделью, нужна единая оркестрация
с общим счётчиком расписания и бюджета. Повторный независимый запуск этой
функции начинает новый счётчик; его нельзя использовать как вложенный цикл,
если общий предел на пользовательский запрос остаётся три генерации.
Подключение бюджетных исправлений в этой задаче не реализовано.

## Воспроизведение без сети

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_ai_planning.py -q
.\.venv\Scripts\python.exe -m pytest -q
```

`tests/test_ai_planning.py` вызывает публичную функцию с синтетическим транспортом,
реальной проверкой ответов и `check_schedule`. Проверяются успех, исправление
часов/длительности/пересечений и переходов, лимиты 1–3, смешанные повторы,
unknown, ошибки API, невозможность подставить длительность модели и отсутствие
вложенных повторов SDK через FakeClient. Часы и оценки переходов, изменённые
в тестовых объектах, синтетические и не записываются в каталог.

Для ручного offline-сценария передайте `transport=lambda *_: raw_json`, где
raw_json содержит синтетический PlanDraft с ID текущей выборки. Проверьте
status, schedule_check.issues и metadata.attempts; для исправления используйте
транспорт, возвращающий по очереди неверный и исправленный JSON. Примеры
таких сценариев находятся в тестах. Это инструкция для повторения, а не
утверждение о выполненной ручной проверке UI или живом Gemini-прогоне.

Новых live-результатов в eval/results нет. Актуальность каталога, качество
Gemini-исправлений, бюджет, UI и готовность checkpoint этим прогоном не доказаны.

Фактически выполнено 26 ноября: 29 новых тестов; релевантный набор AI и
расписания 111 passed, полный pytest -q 200 passed in 2.65s; pip check без
