# Общий формат запроса и результата

Версия проекта контракта: `1.1-draft`. Обновлён 16 ноября 2026 года в рамках порученной общей основы. Модели реализованы в `src/contracts/models.py`; полный продукт и AI-вызов ещё не реализованы. Версия 1.1 добавляет явный режим demo и конкретные вложенные форматы. Допущения MVP по-прежнему требуют согласования команды. Учебный пример в `src/demo.py` использует условное место без вымышленных реальных источников и цен.

## Поток данных и владельцы

В одном локальном Python-приложении UI Рахата передаёт `TripRequest` оркестратору Ернура. HTTP API для MVP не нужен. Оркестратор проверяет вход, получает сведения каталога, вызывает модель и принимает только структурированный `PlanDraft`. Проверки расписания Ернура и бюджета Рахата возвращают нарушения. Модель может исправить план; предлагаемый предел — три генерации всего, включая первый ответ. Итоговый `TripResult` собирается приложением из проверенного расписания, данных каталога и расчёта бюджета и возвращается UI.

Сетевой ключ модели не передаётся через форму или контракт. UI не показывает сырые ответы LLM как проверенный маршрут. AI не устанавливает цены, суммы, URL и статус успешной проверки.

Предлагаемые функции границы модулей (пока только названия):

| Граница | Вход → выход | Владелец |
| --- | --- | --- |
| UI → оркестратор | `TripRequest` → `TripResult` | Рахат / Ернур |
| Поиск каталога | даты + интересы → существующие `Place` и `Source` | Ернур |
| Модель → оркестратор | структурированный `PlanDraft` | Ернур |
| Проверка расписания | запрос + черновик + каталог → `ScheduleCheck` | Ернур |
| Расчёт/проверка бюджета | запрос + черновик + ценовые записи каталога → `BudgetSummary` | Рахат |
| Проверки → модель | коды нарушений и необходимые сведения без секретов → исправленный черновик | Ернур |

Общие модели `src/contracts/` и изменение полей согласуют оба. При смене значения, обязательности или типа поля обновить версию контракта и проверки обеих сторон. До согласования версии нельзя независимо реализовывать разные форматы.

## Общие соглашения

- Имена полей в `snake_case`, при сериализации — JSON. Обязательные поля передаются всегда; неизвестные скалярные значения — `null`, списки без элементов — `[]`. Не использовать `0`, пустую строку или «примерно» вместо неизвестного числа.
- Деньги — целое неотрицательное число тенге; валютный код только `KZT`. Для сумм, которые неизвестны, используется `null`. Бесплатно — `0` только при подтверждённой бесплатности.
- Даты — `YYYY-MM-DD`, время в расписании — `HH:MM` по `Asia/Almaty`. Дата и время проверки источника — ISO 8601 с часовым смещением, только фактически выполненная проверка. Дедлайны курса к этому правилу не относятся.
- ID — непустые строки, уникальные в своём реестре; ссылки между объектами проверяются. Модель использует выданные каталогом ID, не создаёт новые места или источники.
- Версия каталога и версия промпта — обязательные идентификаторы снимка/редакции при генерации; их значения присваиваются при реальном создании, не заранее.
- Предложенные ограничения MVP: один взрослый, русский язык, визиты в пределах одного дня без перехода через полночь, временное окно дня 09:00–20:00. Это проектные допущения, а не предпочтения уже опрошенного пользователя; согласовать с командой до реализации. Не включать удалённые горные поездки с непроверенными переходами только потому, что они рядом с Алматы.

## TripRequest — что передаёт интерфейс

| Поле | Тип | Правило |
| --- | --- | --- |
| `schema_version` | строка | Только `1.1-draft` в текущей основе. |
| `start_date` | дата | Обязательна; не задавать неизвестную дату за пользователя. |
| `end_date` | дата | Обязательна; включительно, от 1 до 3 календарных дней со start_date. |
| `budget_kzt` | целое > 0 | Общий лимит на всю поездку одного человека, не дневной. |
| `interests` | массив уникальных кодов | Хотя бы один код из согласованного списка. |
| `city` | строка | Только `Almaty` в MVP. |
| `currency` | строка | Только `KZT`. |
| `travelers` | целое | Только `1` в предлагаемом MVP. |
| `language` | строка | Только `ru` в предлагаемом MVP. |

Предлагаемый список интересов: `culture`, `history`, `nature`, `food`, `walking`. Ернур согласует теги с наполнением каталога, Рахат — подписи формы. Свободный текст для MVP не обязателен; если его добавят, считать его недоверенными данными и ограничить длину. Лишние/неизвестные поля и коды отклонять, не молча преобразовывать.

UI будет проверять обязательность и типы, оркестратор повторит проверку независимо. TripRequest уже проверяет настоящие календарные даты и end_date ≥ start_date с включительной длительностью ≤3. Проверка «не в прошлом» пока не включена в общую модель: это предложенное продуктовое правило, а также сохранённые evaluation-запросы должны оставаться читаемыми. После согласования проверять его на границе будущего оркестратора по времени Алматы. Верхний горизонт планирования остаётся открытым. При будущих датах источник не гарантирует будущую цену или открытие; выводить оговорку.

## Каталог, предоставляемый AI и валидаторам

### Source

`source_id`, `url`, `title`, `publisher`, `checked_at`, `supports` — обязательные поля записи источника. `supports` перечисляет ID места/ценовой записи, название факта и краткое извлечённое значение. URL и checked_at добавляются только после реального открытия и проверки страницы. При наличии записывать `published_at`/`valid_until`, иначе `null`. Дата просмотра не равна дате актуальности цены.

Записывать только необходимый короткий факт, не копировать весь сайт. Перед использованием проверить допустимость источника и лицензии/условий. При расхождении источников сохранить расхождение и не выдавать спорный факт как подтверждённый.

### Place

| Поле | Тип и смысл |
| --- | --- |
| `place_id`, `name` | Стабильный ID и проверенное название. |
| `interest_tags` | Коды из общего списка интересов. |
| `address` | Проверенный адрес или `null`. |
| `coordinates` | Объект latitude/longitude или `null`; без координат не обещать проверенные переходы. |
| `visit_duration_minutes` | Положительное целое; редакционная оценка с явной пометкой, если не из источника. |
| `opening_hours` | Интервалы по дням недели, исключения по датам и поддерживающие `source_ids`, либо `null`. Пустой список интервалов на конкретную дату означает «закрыто», null — «неизвестно». |
| `entry_price` | `CostBasis` для входа; не только число. |
| `fact_source_ids` | Соответствие «название/адрес/координаты/длительность/описание» → массив ID источников. Отсутствующая поддержка явно видна. |

`CostBasis`: `basis_id`, `category` (`entry`, `food`, `transport`), `amount_kzt` (число либо null), `kind` (`published_price`, `editorial_estimate`, `unknown`), `source_ids`, `assumption` (строка либо null). Для редакционной оценки явно указать правило и происхождение; не приписывать сайту цену, которую он не публиковал. Для `unknown` amount_kzt=null. Для опубликованной цены обязательна поддержка источником. Питание и местные переходы также получают записи CostBasis в каталоге/реестре, чтобы Рахат мог считать их без выдумок модели.

В первом MVP допускаются ручные консервативные оценки переходов, если метод и ограничения раскрыты. Проверка географии и темпа не равна расчёту реального маршрута на карте. При неизвестном времени перехода проверка расписания остаётся неполной.

## PlanDraft — что возвращает модель внутри приложения

Модель получает TripRequest, отобранные места с фактами и ID источников, ценовые основания и сообщения проверок. Тексты источников не могут менять системные правила или вызывать произвольные инструменты.

| Поле | Тип и правило |
| --- | --- |
| `days` | По одному объекту на каждую дату запроса, в порядке дат; без пропусков. |
| `days[].date` | Дата из диапазона запроса. |
| `days[].activities` | Упорядоченный массив визитов, питания и перерывов. |
| `activities[].activity_id` | Уникальный ID позиции внутри результата. |
| `activities[].kind` | `visit`, `meal` или `break`. |
| `activities[].place_id` | Существующий ID, обязателен для visit; для meal/break может быть null. |
| `activities[].start_time`, `end_time` | Локальное время; start < end в рамках даты. |
| `activities[].reason` | Краткая связь с интересами пользователя; не добавлять неподтверждённые факты. |
| `activities[].source_ids` | Только предоставленные ID источников, поддерживающих фактическое объяснение. Сам список ещё проверяет приложение. |
| `activities[].cost_basis_ids` | Существующие основания расходов; отсутствие обязательной категории не считается нулевой стоимостью. |
| `days[].transfers` | Переходы между соседними активностями. |
| `transfers[]` | `from_activity_id`, `to_activity_id`, `duration_minutes` (целое или null), `method` (`catalog_estimate` или `unknown`), `cost_basis_ids`. |
| `assumptions` | Явные ограничения/допущения модели; факты каталога ими не заменять. |

Модель не возвращает готовую общую сумму, новые URL или цены для использования без проверки. Если сырой ответ содержит такие значения, приложение не принимает их за расчёт или источник. Недопустимые поля и несуществующие ID приводят к ошибке валидации/коррекции, а не к дополнению каталога.

Инструменты AI-цикла: поиск по каталогу, проверка расписания, запрос расчёта бюджета. Допускается явная оркестрация вызовов кодом вместо сложного фреймворка. В обоих случаях AI должен получать обнаруженные ошибки и содержательно пересматривать план, а не только писать объяснение готового фильтра.

## Проверки и BudgetSummary

`ScheduleCheck`: `status` = `valid` / `invalid` / `unknown`, массив `issues`. Валидатор проверяет диапазон и число дней, наличие активностей, порядок и пересечения, длительность визитов, часы и исключения, время переходов и необоснованные повторы места. `unknown` означает недостаток данных; это не успешная проверка.

Каждая `issue`: `code`, `message`, `date` (или null), `activity_id` (или null). Коды должны быть стабильными, текст можно менять. Предлагаемые коды: `MISSING_DAY`, `UNKNOWN_PLACE`, `TIME_OVERLAP`, `OUTSIDE_OPENING_HOURS`, `UNKNOWN_OPENING_HOURS`, `INSUFFICIENT_TRANSFER_TIME`, `UNKNOWN_TRANSFER_TIME`, `MISSING_COST`, `OVER_BUDGET`, `UNSUPPORTED_CLAIM`.

`BudgetSummary` собирается модулем Рахата:

| Поле | Смысл |
| --- | --- |
| `currency`, `limit_kzt` | KZT и исходный лимит. |
| `items` | Все расходы поездки: вход, питание и транспорт без повторного учёта. |
| `items[]` | `cost_item_id`, `date`, `activity_id` или пара ID перехода, `category`, `basis_id`, `quantity`, `unit_amount_kzt`, `amount_kzt`, `kind`, `source_ids`, `assumption`. |
| `known_subtotal_kzt` | Сумма всех известных amount_kzt. При неизвестных расходах это только известная часть. |
| `unknown_cost_item_ids` | ID всех позиций без суммы; пропущенная обязательная категория создаёт неизвестную позицию/ошибку. |
| `total_estimate_kzt` | Сумма всех позиций, если они известны; иначе null. Редакционные оценки допустимы при явной маркировке. |
| `budget_status` | `within_budget`, `over_budget` или `unknown`. |
| `remaining_kzt` | limit − total, если полный расчёт есть; иначе null. Может быть отрицательным. |
| `issues` | Ошибки/неопределённость для AI и UI. |

quantity — положительное целое, для одного путешественника обычно 1. unit_amount и amount — неотрицательные целые или null. amount = quantity × unit_amount; округление при вводе оценок заранее согласовать, не округлять разные итоги независимо. Каждая платная активность/транспортный участок учтены один раз; один источник может поддерживать несколько разных расходов. Перерывы без затрат обозначаются явно, отсутствие цены не трактуется как бесплатно.

Если есть неизвестные позиции, но known_subtotal > limit, budget_status=`over_budget`. Иначе при неизвестных позициях status=`unknown`. При полном расчёте status определяется сравнением total с limit (равенство допускается). Дневные суммы и общие категории считаются тем же модулем по тем же items, UI не пересчитывает другим алгоритмом. Любая итоговая стоимость остаётся оценкой, не предложением оплаты.

## TripResult — что получает интерфейс

Обязательная оболочка:

| Поле | Тип и назначение |
| --- | --- |
| `schema_version` | Согласованная версия контракта. |
| `status` | Одно из значений ниже. |
| `message` | Понятное объяснение результата/ошибки на русском. |
| `request` | Валидированный TripRequest или null при неверном вводе. |
| `itinerary` | Массив проверенных/частично проверенных дней или null. |
| `budget` | BudgetSummary или null. |
| `schedule_check` | ScheduleCheck или null. |
| `sources` | Реестр только использованных источников с URL, checked_at и поддерживаемыми фактами. При ошибке может быть []. |
| `warnings` | Массив кодов и текстов про цены, часы, оценки, свежесть и ограничения. |
| `errors` | Массив кодов/сообщений ошибок с полем ввода/активности при наличии. Никаких ключей, служебного traceback или сырого запроса провайдера. |
| `metadata` | `catalog_version`, `prompt_version`, `model` (строки или null), `attempts` (целое ≥0), `mode` (`ai`, `baseline`, `demo`). Для demo/baseline модель null и попыток 0. Для AI с выполненным вызовом обязательны модель и версии. |

В `itinerary` приложение обогащает дни/активности из PlanDraft проверенными названиями мест, ссылками на соответствующие `sources` и ID расходов из `budget.items`. Дневной итог берёт из расчёта Рахата; при неизвестной дневной стоимости итог null и отдельно известная часть. Переходы сохраняются. Объяснение модели проверяется на фактическую поддержку; неподдержанные утверждения удаляются/исправляются до вывода или вызывают ошибку, а не превращаются в «предупреждение» при общем успехе.

| status | Когда возвращать | Поведение UI |
| --- | --- | --- |
| `ok` | Все дни и факты валидны, schedule valid, полный бюджет within_budget | Показать маршрут, детализацию и источники; назвать расходы оценкой. |
| `partial` | Структурно пригодный маршрут есть, но часы/переходы/часть расходов неизвестны | Явная пометка неполной проверки; не обещать соответствие бюджету/часам. |
| `infeasible` | После ограниченных попыток в проверенном каталоге не удалось получить допустимый план, например из-за бюджета/закрытий | Объяснить ограничения и возможное изменение запроса; itinerary=null, не предлагать заведомо невалидный маршрут. Не утверждать, что поездка невозможна вообще. |
| `invalid_request` | Вход не прошёл проверку | itinerary/budget/schedule=null, ошибки рядом с полями, API не вызывать. |
| `service_error` | Нет доступа, таймаут, лимит, сбой данных/модели или невалидный ответ после попыток | itinerary/budget/schedule=null, понятная ошибка и возможность повторить; не маскировать как infeasible. |

Расписание с известным нарушением не может получить partial или ok. Известное превышение бюджета не является partial: исправить или вернуть infeasible. Если одновременно неизвестны часы и полностью известный бюджет не превышен, допустим partial, но общая готовность маршрута не подтверждена. Ошибка данных каталога — service_error, а не вина пользователя. Конкретные таймауты и правила повторов по сетевым ошибкам согласовать после проверки квот; они не должны создавать неограниченные платные вызовы.

## Критерии совместимости перед интеграцией

- [ ] Оба подтвердили допущения (число людей, язык, окно дня, интересы, горизонт дат) и обязательные поля.
- [ ] Рахат может отобразить все статусы, неизвестные суммы и источники без разбора свободного текста.
- [ ] Ернур получает машинные ошибки бюджета и расписания для исправления плана; LLM не может объявить собственный ответ проверенным.
- [ ] Проверены ссылки ID, число дней и источники фактов; известная сумма, полный итог и неизвестные затраты различаются.
- [ ] Проверены 1–3 дня, границы дат, равенство бюджету, превышение, неизвестная цена, закрытое место и недоступный API.
- [ ] Примеры/фикстуры для кода создаются позже с честной маркировкой тестовых данных; реальные URL и даты проверки не придумываются.

Интеграционные пункты выше остаются открытыми: тесты общей основы не проверяют реальный каталог, часы, Gemini или расчёт бюджета. Реализована только структурная часть моделей и демонстрационный путь; результат проверок см. в логе основы. Согласование всех продуктовых допущений обоими участниками ещё предстоит.

## Конкретизация вложенных моделей в версии 1.1

- `SupportedFact`: `entity_id`, `field`, `value` — непустые строки. `Source.supports` — непустой список таких записей. `published_at` и `valid_until` — ISO datetime с часовым смещением или null. `url` — HTTP(S), но корректный синтаксис не доказывает, что страницу открыли или что она поддерживает факт.
- `Coordinates`: latitude от −90 до 90, longitude от −180 до 180. `OpeningHours`: `weekly` с ключами mon–sun, `exceptions` с ключами дат YYYY-MM-DD, `source_ids`. Значения weekly/exceptions — интервалы `{start_time, end_time}`, [] означает закрыто, null или отсутствующий ключ — неизвестно. Интервалы в рамках одного дня.
- `CostItem` всегда содержит `activity_id`, `from_activity_id`, `to_activity_id`: либо activity_id заполнен и оба поля перехода null, либо activity_id=null и заполнена полная пара перехода. Все остальные поля перечислены в BudgetSummary. Сам расчёт quantity × unit_amount и сумм выполняет будущий модуль бюджета, а не общая модель.
- `ResultActivity` расширяет Activity полями `place_name` (строка или null), `cost_item_ids` (массив ID). `ResultDay` расширяет DraftDay полями `known_subtotal_kzt` и `total_estimate_kzt` (число либо null); activities содержит ResultActivity. URL не дублируется в каждой активности: UI связывает source_ids с TripResult.sources.
- `Notice`: `code`, `message`. `ResultError` дополнительно содержит `field`, `activity_id` (строки или null). Все nullable-поля обязательны в JSON, неизвестные значения передаются как null. Лишние поля запрещены, денежные значения не преобразуются из строк, bool или дробей.
- `demo` — только условный учебный пример: видимая пометка в UI, без модели, источников и заявлений о проверенных местах. Текущий пример возвращает partial с неизвестным бюджетом и расписанием; статус ok в режиме demo запрещён. Дата примера — завтра по Asia/Almaty; это демонстрационная дата, не выбранная пользователем поездка.

Общие модели проверяют форму, отдельные ссылки и согласованность статусов, но не заменяют будущие проверки фактов, источников, полноты расходов, арифметики, часов, переходов и существования ID в реальном каталоге. Успех Pydantic не означает готовность маршрута.
