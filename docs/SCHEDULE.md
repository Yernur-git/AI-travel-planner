# Проверка расписания

Владелец: Ернур. Реализовано и проверено offline 25 ноября 2026 года в
`feature/schedule-validation`. Общий контракт `1.1-draft` не изменён.

Публичная функция:

```python
from src.schedule import check_schedule

check = check_schedule(request, draft, catalog_selection)
# request: TripRequest; draft: PlanDraft; catalog_selection: CatalogSelection
# check: существующий ScheduleCheck; check.model_dump(mode="json") для обмена
```

Передавать полный снимок `load_catalog().search()` без фильтра интересов/дат,
чтобы отфильтрованное место не считалось отсутствующим. Входы должны пройти
существующие модели: ошибки формы дают Pydantic ValidationError. Функция повторно
проверяет request/draft, поэтому изменённые после создания модели тоже проверяются.
Пустые дни, повторные даты/ID и start >= end отклоняет контракт до проверки фактов.
Функция не изменяет входы, не читает `.env` и не обращается к сети.

Проверяются точные даты запроса, существование каждого ненулевого place_id,
порядок и все попарные пересечения, минимальная длительность visit из каталога,
часы для любой активности с местом, исключения и повторы визитов за всю поездку.
Длительность каталога считается минимальным резервом, как в проверке Gemini;
текущие значения являются редакционными оценками, не измерением темпа.
Соприкасающиеся интервалы часов объединяются; разрыв, например обед, не перекрывается.
Начало в момент открытия и окончание в момент закрытия допустимы.
Исключение на дату имеет приоритет над неделей, включая null и [].
Необоснованный повтор visit считается нарушением: свободный reason/assumptions
не даёт проверяемого основания для исключения.

`invalid` имеет приоритет над `unknown`: обход собирает все обнаруженные
нарушения и пробелы, не останавливается на первой неизвестности. `valid` означает
отсутствие нарушений и неизвестных данных в пределах этих проверок. Это не
подтверждение бюджета, фактической актуальности сайтов, кассовых правил,
очередей или общей готовности TripResult. Условие кассы до 17:30 хранится только
в тексте источника; контракт не имеет структурированного поля для его проверки.
Тексты источников не интерпретируются как новые правила часов.

Переход нужен для каждой соседней пары в направлении массива активностей.
Пропущенный, повторный и несоседний/обратный переход являются нарушениями.
Порядок записей transfers сам по себе не влияет на проверку: важны пары ID.
Для каждой пары проверяется свободное время end предыдущей → start следующей.
Без независимой оценки длительности результат для пары unknown, даже если
модель указала method=catalog_estimate или между активностями нет зазора.
Нулевой зазор не доказывает физическую невозможность без данных о переходе.
Отсутствие места у meal/break не означает пребывание в предыдущем месте.

Для будущих независимых оценок есть необязательный Python-аргумент
`transfer_estimates`: отображение направленной пары `(from_place_id, to_place_id)`
в `TransferEstimate(duration_minutes, assumption)`. `assumption` обязательно
описывает метод, происхождение и границы применимости; длительность целая >=0.
Это локальный вспомогательный тип модуля, не изменение JSON-контракта или
реестра данных. Его заполняет доверенный вызывающий код, а не ответ модели.
Даже при transfer.method=unknown доверенная оценка позволяет проверить зазор.
Ни одной реальной оценки в текущей задаче не добавлено. Статические оценки
применяются только там, где вызывающий код подтвердил их применимость к поездке;
они не вычисляют расстояния, пробки или маршрут. При нехватке зазора возвращается
INSUFFICIENT_TRANSFER_TIME, включая случаи других неизвестных данных.

Стабильные коды известных нарушений: `MISSING_DAY`, `UNEXPECTED_DAY`,
`UNKNOWN_PLACE` (несуществующий ID, поэтому invalid), `ACTIVITY_ORDER`,
`TIME_OVERLAP`, `VISIT_TOO_SHORT`, `OUTSIDE_OPENING_HOURS`, `REPEATED_PLACE`,
`MISSING_TRANSFER`, `DUPLICATE_TRANSFER`, `INVALID_TRANSFER`,
`INSUFFICIENT_TRANSFER_TIME`. Коды неполноты: `UNKNOWN_OPENING_HOURS`,
`UNKNOWN_TRANSFER_TIME`. Каждая issue содержит дату и ID активности либо null,
как требует существующий контракт. Дополнительного поля severity нет;
потребителю следует использовать status и коды, не разбирать текст message.

## Воспроизведение offline

Из корня проекта, без Gemini и ключа:

```powershell
@'
import json
from pathlib import Path
from src.catalog import load_catalog
from src.contracts.models import PlanDraft, TripRequest
from src.schedule import check_schedule
saved = json.loads(Path('eval/results/gemini-first.json').read_text(encoding='utf-8'))
selection = load_catalog().search()
assert selection.catalog_version == saved['metadata']['catalog_version']
check = check_schedule(TripRequest.model_validate(saved['request']),
                       PlanDraft.model_validate(saved['draft']), selection)
print(check.model_dump_json(indent=2))
'@ | .\.venv\Scripts\python.exe -X utf8 -
.\.venv\Scripts\python.exe -m pytest -q
```

Реально выполнено: сохранённый PlanDraft проверен по текущему каталогу;
версия совпала с metadata исходного запуска. Результат в
[schedule-first.json](../eval/results/schedule-first.json): `unknown`, одна
`UNKNOWN_OPENING_HOURS` у Ыхласа, две `UNKNOWN_TRANSFER_TIME`. Известных
нарушений нет; исходный [gemini-first.json](../eval/results/gemini-first.json)
не изменён. Это повторная проверка сохранённого ответа, не новая генерация
и не оценка качества AI на наборе запросов.

Проверки: 41 новый тест, весь набор **166 passed in 1.91s**; `pip check`:
No broken requirements found. Тесты включают границы часов/длительностей,
исключения, закрытия, неизвестные часы, пересечения несоседних активностей,
ошибки переходов, доверенные синтетические оценки и 1–3 дня на границе месяца.
Ручной вызов функции на сохранённом файле выполнен; UI-сценарий не запускался,
поскольку пользовательский поток не менялся. На 25 ноября интеграция в Gemini-цикл,
бюджет и TripResult оставалась отдельной работой. Commit, push, merge не выполнялись.

26 ноября добавлен [ограниченный цикл генерации и проверки](PLANNING.md),

Бюджет, UI и сборка TripResult остаются открытыми.
